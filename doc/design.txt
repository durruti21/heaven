
OVERALL DESIGN
----------------
The design will be composed of the following main blocks:

1 - config 
        The component that stores all the game configuration parameters. The parameters control the behaviour of the rest of components. 
        The config component will read the configuration parameters from the file system configuration files and load them on initialization.
        The config dataset will be split on two subsets:
        - system config dataset -> composed of parameters always readed from file and not modifiable by user (only by MOD)
        - user config dataset   -> composed of parameters modifiable by user

2 - data_store 
        The component that stores all the information realted to a specific game run. The component provides structured access to all the
        information related to a specific game and also provides functions to save or load games into/from the hard disk.
        This information is provided to the active components of the application (game engine and game gui).

3 - engine
        The game engine is in charge of running the game simulation, by inspecting the data provided by data_store and updating it.
        The game engine uses the system config dataset with the rules and parameters for executing the simulation.
        The game engine is driven by the game graphical user interface. The engine will receive the actions/decisions the player
        will take in the game run and will update acordingly the data store state. 

4 - gui
        The graphical user interface is the main interface with the user, by providing the information of the game and capturing the
        interactions of the user. Those interactions are grouped in:
        - config management: Modify the user config dataset to be used.
        - game management: Load or Save a game run into/from the data_store object
        - engine management: Control the execution of the game engine
        - display management: Show all the information related to the data store to the user.
        - control management: translate the interactions of the player to actions/decisions for the game engine.

5 - ai_agents
        The ai agents component is intended to store a set of agents that allows the manipulation of the data_store in the same
        way that the user interacts with the gui to control the simulation data. The ai agent is intended to provide:
          - Adversaries to the player.
          - Generation of scenarios on the game setup (i.e. system creation)
          - Generation of random simulation data during the simulation (i.e. images) 
        The ai agents will be created/deleted by the game engine when the appropiate conditions occur.

6 - support
        This component stores all the infrastructure classes used by the rest of the components, providing
        cross component services.
        

CONFIG
-------------------------------------------------
The config object will be composed of a parent object that will compose the different configuration files.
The overall architecture will be of having a separate class to parse each file and provide methods to get or set 
this parameters. The main access point to the component will be the ConfigData class that will expose its child 
as public methods.

To ensure robustness, all the parameters inside a class will have a default value, so if the file is missing, corrupt,
or does not include the specifc parameter, the default value will be used.

The configuration files will be JSON files parsed by the nlohmann/json library (ref. https://github.com/nlohmann/json).
The files will be stored on the ./config directory of the game.

The files that are identified are:
- application.json : Game application configuration (i.e. language, video, sound, etc)
- setup.json : Simulation run initial conditions (i.e. start date) 


DATA STORE 
--------------------------------------------------
The Data store is the main component that stores the simulation data. The main operations that the Data Store provides
to their users are:
- Create New Game: Generates a new initial data set based on the  Config data and any associated generation algorithm.
- Load Game: Loads a game from a saved simulation file in a predefined folder.
- Save Game: Stores the simulation data in a file on a predefined folder.
- Create Parameter(s): Create function for some parameters that can have a limited life span on the simulation 
- Set Parameter(s): Set functions for each specific parameter that is modified by the users of the component
- Get Parameter(s): Get functions for each specific parameter that is required by the user
- Delete Parameters(s): Delete function for some parameters that can have a limited life span on the simulation.

The dataset of each game is composed of:
- Time Data
- System Body info Data


ENGINE
--------------------------------------------------
The engine is the main component that is in charge of executing the simulation. It has all the logic necessary
to process and update all the data related to the simulation.

The engine is composed on several subcomponents, each one in charge of updating one aspect of the data. 
Special caution must be keep on the engine to ensure that the data is updated consistently so no closed loops
of information are stablished.

The simulation is driven by two parameters. The tick, that is the minimum amount of time simulated, and the increment,
that is a multiple of ticks. This approach is used to provide flexibility on the execution.

The engine is driven by the GUI, that tells the engine when it has to run and how much steps must run.
In that sense, the commands that receives from the GUI are:
- Set Simulation Time: Establishes the time increment in ticks.
- Set Execution Mode: Single tick or continous
- Execute: Executes the simulation in the mode and time established
- Stop: Stop the simulation

Not all the aspects of the simulation will be executed on each increment. Depending on the aspect, some fixed ticks
will be used for each aspect. The tick and the associated aspects update will be driven by configuration.

As the engine must run in decoupled mode from the GUI, an internal thread will be used to run the engine.


GUI
--------------------------------------------------
The GUI component is the interface with the user.  It relies on SDL3 and Imgui library to perform the graphical output
and capturing user inputs. The component is divided on:
- gui_console: A debug console activated by TAB key
- gui_icons: definition of icons used on the GUI interface.
- gui_main: The object that stores the main loop interaction with the SDL and IMGUI initialization/shutdown and loop main procedures
- gui_map: The simulation main map
- gui_map_camera: The control of map camera.
- gui_sim_interface: The simulation interface menus. Control of Simulation Time.
- gui_item_display: The component to display an item information

Each component will have the proper draw and event handling components.

Other components will be identified in the future

SUPPORT
--------------------------------------------------
The support component is a set of classes with cross functional infrastructure used by the rest of the main components.
The list of services that provides are:
- logger function. Provide logger services for the rest of the components. The policy to use the log shall be:
        - critical: Errors that prevent normal working of application and ends in termination. All conditions must be logged
        - warning: Messages that do not prevent normal working but should indicate a failure. All conditions must be logged.
        - info: Messages of normal application run that are significative (i.e. load data, initialization, user actions). All must be logged.
        - debug: Messages inserted only for debugging purposes. Normally only inserted to test problems on application.
